# Runtime verdict bitmap transfers

This natural C++ proposal has one retained native producer for the two real
MAINE device-copy functions. It makes no claim of exact bytes, original
handwritten-assembly authorship, or successful hardware execution. The original
complete boundaries are capture `E3A4..E3CF` (43 bytes) and restore
`E3CF..E422` (83 bytes), each near Pascal with one unsigned word argument and
`RET 2`. The complete original cohort is 126 bytes, without NOPs or CODE tables.
Original ordered MZ fixups are [] for capture and [46, 14] for restore.

The real runtime array is `verdict_bitmap[2][352][40]`, all unsigned bytes.
`staff.cpp` already owns that complete 28160-byte BSS object; this header only
redeclares its identical type. Its original near address range is DS
`56D8..C4D8`. It is runtime raster storage, with no initialized image bytes in
this producer and no initialized-DATA credit. The controller supplies byte
offsets from zero through 14080, including intermediate scroll positions;
the offset is not restricted to a screen index. One complete capture or restore
uses 14080 consecutive buffer bytes and stays within the two-screen object.
No extra bounds branch absent from the original is introduced.

Capture copies the first 40 bytes of each of 352 VRAM rows from segment
`E000`. The real VRAM row stride is 80 bytes, while RAM rows are packed at 40.
Restore selects GRCG TDW mode with tile color1, writes the same 352-by-40-byte
rectangle at segment `A800` with the real 80-byte row stride, then selects
RMW mode/color13 and writes the saved bitmap as its mask. Only after that mask
copy does it disable GRCG through the original port `7Ch` operation. It does
not clear another region or toggle GRCG around individual rows.

The original TDW clear happens to reuse AX=`A800` as its CPU word data after
selecting ES. TDW obtains visible color from the tile registers and ignores
that incoming CPU data. The maintained fill therefore uses the natural zero
value; it does not invent a meaningful `A800` pixel pattern to reproduce an
incidental instruction allocation. Under RMW, copied bitmap bits are meaningful
write masks, so the entire forty-byte source row is retained.

The installed and active TC4 `MEM.H` copies have identical SHA256
`e4beea2052d88ffff7a1727b6c13278a226675a427aac3d48d63532c34be552b`.
Lines93–94 declare the real `__memcpy__` and `__memset__` intrinsics, with
far data pointers in the selected large model and a two-byte `size_t` length.
The source uses those installed APIs, canonical byte types, ordinary local
pointers, row counts and row increments. It contains no assembly body,
register arithmetic, explicit SI/DI selection, emitted opcodes or target byte
arrays. The existing OP `nopoly_B_put()` supplies a genuine intrinsic precedent;
its complete 30-byte helper remains unaccepted because two XOR encodings differ.
That precedent does not establish these new functions' emitted code or length.

The far-pointer types carry the real source and destination segments. This
proposal does not manually change DS, so preserving caller DS is the intrinsic
and compiler ABI's responsibility. Native original capture saves/restores DS,
uses E000 as source DS and incoming DS as destination ES; restore uses A800 ES
and caller DS as source. Both originals rely on the normal forward DF=0
convention and preserve SI/DI. The one retained producer has now been inspected: the intrinsic honors both
far-pointer segments and preserves DS around each row copy. The static details
and remaining limits are recorded below. The device algorithms have not been
executed, and no explicit hardware bridge has been added.

The proposed shared cohort negative changes only capture's forty-byte copy to
thirty-nine bytes, retaining both real row strides and the full buffer type.
Restore has no independently compiled mutation. Neither candidate is registered
or accepted, and neither receives a claim of 43/83 generated bytes. A future
coherent frame/copy/controller TU may provide useful real source context, but
its record layout cannot justify changed algorithms, invented lengths, filler
or relocation reordering. The primary candidate reference is
`ReC98/th05/end/verdict_bitmap.asm`; it is not proof of original source language.
Private native metadata and a diagnostic-only proposal are under
`.analysis/maine-staff-bitmap/`.

## One actual producer

The only actual C++ producer is
`.analysis/native-producers/maine-staff-bitmap-b/`. An earlier assembly-scaffold
attempt stopped on a missing `ASSUME CS`; it supplies no additional C++ producer.
The retained complete actual functions are capture `E3A4..E3E9` (69 bytes) and
restore `E3E9..E477` (142 bytes), 211 total. Both end in the real near Pascal
`RET 2`, with saved SI/DI and no NOPs. Their original 43/83-byte extents have
not been reproduced. No second producer or negative was run, and nothing was
registered or accepted.

Capture stores the incoming DS in the destination far pointer and constant
E000 in the source far pointer. Each row installs ES with `LES`, selects the
source segment in DS, copies twenty words, and restores the caller DS with
`PUSH DS`/`POP DS`. RAM advances forty bytes, VRAM eighty, and the loop runs
352 times. The final ES is the incoming RAM segment, as in the original.

Restore's first loop installs A800 with `LES`, zeroes AX and writes twenty
words per row in TDW/color1. Its second loop again installs A800 ES and selects
the captured incoming RAM segment as source DS for twenty-word copies, with
DS saved/restored per row. Both loops run 352 rows with the declared 80/40-byte
strides. Actual far calls still target the real `0000:0F28` graphics provider;
its original routine does not change DS. Only after the mask loop does the
source disable GRCG through `OUT 7Ch,0`. No CLD or STD is inserted; the normal
forward DF=0 assumption remains the same as the original. No mismatch in this
static device-transfer algorithm was found. This is not a runtime observation.

The diagnostic binder reserved the original 126-byte contribution before its
fixed tail, while the actual contribution occupies 211 bytes. Consequently the
following diagnostic DGROUP lands at `1017`, rather than the original `1011`;
its real `_verdict_bitmap` label is `1017:56D8`. The generated pointer captures
incoming DS instead of hardcoding either segment, so its relative complete
BSS addressing is correct for that producer. Original RAM linear placement is
not reproduced, and no execution with the original DS is claimed. This layout
drift must remain visible independently of the successful intrinsic audit.

Private replayable audit `.analysis/maine-staff-bitmap/diagnose_b.py` validates
the saved MAP/MZ/OMF, actual arguments, source and binding identities, then
records the full emitted functions and checks these segment/loop properties.
Its `diagnostic-b-review.json` preserves the diagnostic receipt hash. CPP/HPP
and binder inputs were unchanged by this audit; no algorithm, copy length,
register allocation, padding or additional build was tried.

## Segment-qualified capture candidate

`bitmap_snap_segmented.cpp` independently keeps the full buffer and real
Pascal argument while selecting E000 as source DS and entry DS as destination
ES once. Its ordinary near source pointer and `__es` destination pointer retain
the two-byte offsets; installed `__memcpy__` supplies each forty-byte row copy.
Only the real DS save/restore and segment transition are explicit hardware
operations. No physical SI/DI algorithm, new guard or fabricated pixel data
is introduced. The original two-function candidate remains unchanged.

The first successful direct producer emits 58 bytes, versus the earlier
capture's 69 and the native 43. Actual disassembly confirms one DS save and
restore around all 352 copies of twenty words, source stride 80 and destination
stride 40, with preserved BP/SI/DI and ES left at the RAM segment. The remaining
extra code holds the row count on the stack, transports BX/DX cursors into
SI/DI each row, and uses a longer frame and ES assignment. This is static
evidence only; no device execution or additional model was run.

An ordinary `register` declaration for both pointers produces the same 58 raw
bytes. The first source was restored byte-for-byte. Its current diagnostic is
`.analysis/native-producers/maine-bitmap-snap-segmented-a/`. Neither trial passed the complete 43-byte
gate; no second positive, negative or acceptance receipt was produced.
The nominal target-sized foreign tail leaves diagnostic DS1012 rather than
native DS1011, and no original whole-layout equality is claimed.

The private proposal stays outside the live manifest. Complete native and
actual instruction/ABI evidence is `.analysis/bitmap-snap-segmented-review.json`,
SHA-256 `5f165995d756e176788172f44be4366cc55f646071fa15b0941dba7692345205`.
This reduces one recovery gap without changing any accepted owner, counter,
initialized DATA, BSS ownership or bitmap-restore implementation.

Its real `E3A4..E3CF` 43-byte capture and `E3CF..E422` 83-byte restore preserve
all row counts, 40-byte data widths, 80-byte VRAM strides, native E000/A800
segment switching, TDW/RMW color controls, REP MOVSW/STOSW, data lifetime,
caller DS, and trailing `OUT 7Ch,AL`. Symbolic constants, the actual bitmap

full span has 56 complete instructions and original ordered fixups `[89,57]`.
The pinned ReC98 `th05/end/verdict_bitmap.asm` is source-language/algorithm
evidence, not proof of an identical historical assembler producer.

contribution and both public function boundaries exactly at original CS A54,

`31` while TASM32 chooses equally semantic `33`. The native relocation order

replay correctly stops at the first positive and does not build a second
producer or negative. Nothing is accepted or credited: no opcode patch, fixup

## 2026-11-10 exact in genuine Turbo C++ original-register context

Both near-Pascal device-copy kernels are **now accepted** as complete functions
through the authentic Staff 20-function compiler object. The previous
standalone TASM attempt above remains a genuine failed *different producer*,
not a reason to reject the present natural compiler result.

`bitmap_hardware_context.inl` preserves the real hand-assembly-style hardware
operations: DS-to-ES RAM snapshot, E000h capture plane, A800h clear plane,
352 rows, 20 WORDs per row, 40/80-byte strides, GRCG TDW/RMW changes and
final port 7Ch disable. C++ compiles the near-Pascal stack frame and SI/DI
saves, while original CPU instructions remain in source-level `asm` blocks.
That avoids the duplicate push/pop pair which produced eight excess bytes in
the first combined context. The resulting two functions match exact native
**43/43** and **83/83** code and literal original far-call relocation order;
no XOR opcode bytes, fixup list or object were manually modified. The real
buffer remains an external DGROUP object at DS56D8, with no stored bitmap
content added by this owner.

Each function passed two fresh TCC/TLINK builds and its own meaningful
negative (352→351 rows, TDW color1→2). Acceptance origin is explicitly C++
**with embedded original-register hardware assembly**, not normal C++ codegen
and not a distinct TASM32-source claim. See [full Staff context](complete_context.md)
for the accepted receipts and original physical MAP proof.
